# Testing PdfReader

Toolchain: Flutter 3.50.0 / Dart 3.14 (`export PATH=/opt/flutter/bin:$PATH ANDROID_HOME=/opt/android-sdk`).

| What | Where | Runs on |
|---|---|---|
| Unit + widget tests | `test/**` | host (`flutter test`) |
| Engine robustness (real PDFium) | `test/qa/corpus_open_test.dart` | host (`flutter test`) |
| Test helpers / fakes | `test/helpers/` | imported by tests |
| Integration tests | `integration_test/` | device / emulator / simulator |
| Test PDF corpus | `test_assets/pdfs/` + `manifest.json` | generated by `tool/testdata/make_corpus.py` |
| CI | `.github/workflows/{ci,android-emulator,ios}.yml` | GitHub Actions |

## 1. Test PDF corpus

The committed corpus (`test_assets/pdfs/`, ~1.3 MB, 246 files) is produced by a dev-only
Python tool. Nothing in it is shipped with the app. The tool is deterministic for a given
`--seed`, except for the AES salts in `password.pdf` and `owner-only-protected.pdf`.

```sh
python3 -m venv /tmp/corpus-venv
/tmp/corpus-venv/bin/pip install -r tool/testdata/requirements.txt   # pikepdf, reportlab, pillow, fonttools, uharfbuzz
# regenerate the committed corpus + integration-test fixtures
/tmp/corpus-venv/bin/python tool/testdata/make_corpus.py --out test_assets/pdfs --clean \
    --dart-fixtures integration_test/fixtures/corpus_fixtures.g.dart
# extras that must NOT be committed (build/ is git-ignored)
/tmp/corpus-venv/bin/python tool/testdata/make_corpus.py --out build/corpus --clean --huge
```

Options: `--fuzz N` (number of mutation files, default 200, 0 = off), `--huge` (huge.pdf with
1,200+ pages and over 100 MB of incompressible noise JPEGs), `--seed`, `--no-malformed`, and
`--font-cache` (default `build/.corpus_fonts`).

**Fonts.** The generator downloads Noto Sans Arabic, Hebrew and Devanagari from the
`google/fonts` GitHub repository (SIL Open Font License 1.1) and keeps them in the font cache. If
the download fails, it uses a system font (GNU FreeSerif, GPLv3 with the font-embedding
exception). The PDFs embed only font subsets, which both licenses allow. Text is shaped with
HarfBuzz (`uharfbuzz`), so Arabic joins and Devanagari conjuncts render correctly. The app itself
never downloads fonts.

**What is in the corpus.** `manifest.json` lists every file with `category`, `expect`,
`failure` (the expected `OpenFailure`), `password`, `pages`, the `text` it must contain,
`features` and `sha256`.

| File(s) | Purpose |
|---|---|
| `tiny.pdf` | 1-page smoke test |
| `text_multi.pdf` | 20 pages: outline (19 chapters × 3 sections), internal links (TOC, "next chapter"), an external `https` link, a `javascript:` URI link, a `/Launch` action, an OpenAction and Names-tree JavaScript, and an embedded file. The word `needle` appears on pages 3, 11 and 18. |
| `scanned.pdf` | 3 image-only pages with no text layer |
| `password.pdf` | AES-256 (R6); user password `test123` |
| `owner-only-protected.pdf` | AES-256 with an empty user password; print, copy and modify are denied |
| `forms.pdf` | AcroForm: text, multiline text, checkbox, radio group, combo box and list box fields |
| `rtl_arabic_hebrew.pdf`, `hindi.pdf` | Shaped RTL and Devanagari text |
| `mixed_rotation.pdf` | `/Rotate` 0/90/180/270; A4, Letter, A5 and landscape pages; a 612×14400 pt page and a 14400×300 pt page |
| `annotated.pdf` | Existing Highlight (with an appearance stream), Ink and Text annotations |
| `malformed/*` (36 files) | Zero-byte, PNG/ZIP/text renamed to .pdf, garbage after header, truncated, bad xref offsets and bad startxref, missing trailer or root, circular Pages tree, objects and outline, 100k-deep nesting, `/Count 1e9`, MediaBox 1e9 / inverted / zero / overflowing, a 1 GiB Flate content bomb, a 20000² image bomb, bad Flate, wrong `/Length`, invalid TrueType/CID/Type3 fonts, broken JPEG/JPX/JBIG2/CCITT/raw images, 300 looping incremental updates, odd names |
| `fuzz/fuzz_000..199.pdf` | Seeded mutations (bit flips, deletes, duplicates, number swaps, token inserts, truncation) of the small seed files |
| `huge.pdf` (on demand) | 1,200 pages, about 120 MB. Never committed. |

`expect` values: `opens`, `needs_password`, `fails` (must throw, mapped to `DocumentOpenException(failure)`),
and `fails_or_opens` (either result is fine; it must never hang or crash).

## 2. Unit, widget and engine tests (host)

```sh
flutter analyze
flutter test                                   # everything under test/
flutter test test/qa/corpus_open_test.dart     # engine robustness only
QA_CORPUS_DIR=build/corpus QA_HUGE_DIR=build/corpus flutter test test/qa/corpus_open_test.dart   # fresh corpus incl. huge.pdf
```

PDFium in `flutter test`: the `pdfium_dart` build hook downloads the PDFium binary (from
bblanchon/pdfium-binaries, SHA-256 pinned) into `build/native_assets/<os>/` on the first run.
Tests then call `initPdfrxForTests()` from `test/helpers/corpus.dart`, which runs the pure-Dart
`pdfrxInitialize()`. `pdfrxFlutterInitialize()` does not work in unit tests because it needs
path_provider.

For every corpus file, `corpus_open_test.dart` opens it (with the password where needed), reads
the page count, renders page 1 at 160 px wide and loads its text. Each step has a time limit
taken from `SecurityLimits` (open 30 s, render 15 s, text 10 s). It also checks the password
flows, permissions, the outline, search hits and link extraction against `LinkPolicy`
(`javascript:` must be blocked).

Outputs:
- `build/qa/corpus_results.json`: per-file outcome (opened, pages, rendered, error, per-stage
  ms, hung), plus a summary and peak RSS.
- `build/qa/corpus_progress.log`: a `START`/`END` line for each file. **If PDFium crashes the
  test process, the last `START` without an `END` is the file that crashed.** A hang is reported
  as a failing test, and the files after it are skipped.
- `build/qa/perf_host.txt` and stdout `PERF ...` lines: open and first-page (1080 px) times for
  `text_multi.pdf` and, if it was generated, `huge.pdf`.

### Test helpers (`test/helpers/`)
- `fakes.dart`: `FakeDocumentService` (uses the real pdfrx engine and maps errors and passwords
  to `DocumentOpenException`), `FakePageEditor`, `FakeSaveService`, `FakeExporter` (TXT uses the
  real text), `FakeIncomingFileService` (`deliver()`), `FakeShareService` and
  `FakeFilePickService` (`pickQueue` / `saveAsQueue`). Every fake records its calls.
- `pump_app.dart`: `pumpApp(tester, {showOnboarding, settings, overrides})` pumps
  `PdfReaderApp` inside a `ProviderScope` with a temporary `AppDirs` and a fake for every
  contract. `TestHarness(useFakes: false)` keeps the real feature implementations and fakes only
  the OS-facing services. `FixedSettingsNotifier` keeps settings in memory.
- `corpus.dart`: manifest loader and `initPdfrxForTests()`.
- `huge_pdf_writer.dart`: `writeHugePdf()` streams a 1,200-page PDF of 100+ MB to disk (for
  devices, where host files cannot be read).

## 3. Integration tests (device / emulator / simulator)

The integration tests do not add PDFs to the release app. `integration_test/fixtures/corpus_fixtures.g.dart`
(generated with `--dart-fixtures`) embeds `tiny`, `text_multi`, `password` and `forms` as base64,
and only `integration_test/` imports it. `launchApp()` copies a fixture into the app's private
inbox and queues it in `FakeFilePickService`, so tapping **Open** on Home opens it. Everything
else uses the real implementations.

```sh
flutter devices
flutter test integration_test/app_flow_test.dart -d <device>        # launch → onboarding → home, open, go to page, search, theme, export TXT
flutter test integration_test/performance_test.dart -d <device>     # scroll + first-page time (numbers in the log)
# Profile-mode numbers, screenshots and JSON report (physical device; emulators/simulators cannot run --profile):
flutter drive --profile -d <device> --driver=integration_test/driver/perf_driver.dart \
  --target=integration_test/performance_test.dart --dart-define=QA_SCREENSHOTS=true [--dart-define=QA_HUGE=true]
```

Dart defines: `QA_HUGE=true` (generates huge.pdf on the device, then measures), `QA_SCREENSHOTS=true`
(only under `flutter drive`; PNGs go to `build/screenshots/`), and `QA_ENFORCE_PERF=true`
(turns the targets into assertions).

### Widget keys (feature code must use these, defined in `integration_test/keys.dart`)
| Screen | Keys |
|---|---|
| Onboarding | `onboarding.next`, `onboarding.done` |
| Home | `home.screen`, `home.open` (calls `FilePickService.pickPdfs`), `home.settings`, `home.recent.<i>` |
| Viewer | `viewer.screen`, `viewer.scroll` (the page scrollable), `viewer.page.<n>` (1-based, on each page widget), `viewer.pageIndicator` (Text "n / m"), `viewer.goToPage`, `viewer.goToPage.field`, `viewer.goToPage.ok`, `viewer.search`, `viewer.search.field` (submits on `TextInputAction.search`), `viewer.search.count` (Text "i of n"), `viewer.search.next`, `viewer.menu`, `viewer.export` |
| Settings | `settings.theme.light`, `settings.theme.dark`, `settings.theme.system` |
| Export | `export.format.<pdf\|png\|jpg\|txt\|docx>`, `export.start`, `export.confirmLossy`, `export.share` (or `export.done`) |
| Password dialog | `password.field`, `password.ok` |

## 4. Reading performance results

Targets: **first page in under 2 s**, and **60 fps scrolling**, meaning the 90th-percentile
frame build time and raster time are both under 16 ms.

- `PERF <key>: firstPage=..ms frames=.. build p90=..ms raster p90=..ms missedBuild=.. missedRaster=..`
  lines appear in the test log and in `build/perf_summary.txt` (under `flutter drive`).
- `build/integration_response_data.json` holds the full `FrameTimingSummarizer` output for each
  key (`text_multi_scroll`, `huge_scroll`): average, p90, p99 and worst build and raster times,
  missed-budget counts, raw frame times and GC counts, plus `<key>_first_page_ms`.
- Only profile builds on real hardware are meaningful. Debug builds and software-GPU emulators
  are much slower, so CI reports their numbers for information only.
- Host engine numbers (`build/qa/perf_host.txt`) isolate PDFium cost from Flutter rendering. On
  the development machine: text_multi open 4 ms, first page 8 ms; huge.pdf (1,200 pages, 120 MB)
  open 115 ms, first page 121 ms.

## 5. CI

- `ci.yml` (every push and PR): analyze, `flutter test` (incl. the corpus), the manifest
  permission check (`tool/security/check_manifest.sh`, if present), a debug APK, and a job that
  regenerates the corpus with `--huge` and re-runs the engine tests on it.
- `android-emulator.yml` (manual, weekly, or PRs that touch integration/android): API 34
  x86_64 emulator on KVM. It generates the corpus with `--huge`, runs the host engine tests,
  `flutter test integration_test/app_flow_test.dart` and the `flutter drive` flow and perf runs,
  then uploads `perf_summary.txt`, the response JSON, screenshots and `build/qa/`.
- `ios.yml` (manual, weekly, or PRs that touch ios/integration): `flutter build ios --no-codesign --debug`,
  boots the newest iPhone simulator, runs the integration tests and the perf drive, and uploads
  the results.
